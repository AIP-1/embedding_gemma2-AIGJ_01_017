# 1부. 공통 기초

## 1-1. AI, 머신러닝, 딥러닝

| 용어 | 뜻 | 관계 |
|---|---|---|
| AI(인공지능) | 사람이 하던 판단을 컴퓨터가 하게 만드는 모든 방법 | 가장 넓은 말 |
| 머신러닝 | 규칙을 사람이 직접 쓰지 않고, **예시 데이터를 보고 컴퓨터가 규칙을 찾게** 하는 방법 | AI의 한 갈래 |
| 딥러닝 | 머신러닝 중 **신경망**(층을 깊게 쌓은 계산식)을 쓰는 방법 | 머신러닝의 한 갈래. 이 프로젝트의 모델은 모두 딥러닝 |

차이를 이 프로젝트로 보면:

- **규칙으로 판단**: 9단계의 "양쪽 손목이 어깨보다 위면 만세". 사람이 기준을 직접 정했다. 머신러닝이 아니다.
- **학습으로 판단**: 9-6단계의 GRU. "만세 영상" 예시를 많이 보여 주면 기준을 컴퓨터가 스스로 찾는다. 머신러닝이다.

## 1-2. 모델이란

**모델**은 입력을 받아 출력을 내는 거대한 계산식이다. 계산식 안에는 조절할 수 있는 숫자가 아주 많이 들어 있고, 이것을 **파라미터** 또는 **가중치**라고 부른다.

- 예: EmbeddingGemma 2 텍스트 부분은 파라미터가 **270M**(2억 7천만 개, M = 백만)이다.
- "모델을 내려받는다" = 이 숫자들이 저장된 파일을 받는다. 2단계에서 Hugging Face에서 받아 `/ssd/hf`에 둔 것이 이것이다.
- 가중치 값이 어떠냐에 따라 같은 계산식이라도 전혀 다른 답을 낸다. 좋은 가중치 값을 찾는 과정이 **학습**이다.

모델을 쓰는 방식은 두 가지다.

| 방식 | 하는 일 | 이 프로젝트에서 |
|---|---|---|
| 학습(training) | 예시를 보여 주며 가중치를 고친다. 느리고 메모리를 많이 쓴다 | 7단계, 9-6단계 |
| 추론(inference) | 가중치는 그대로 두고 입력을 넣어 답만 받는다 | 3~6단계, 8단계, 10단계 |

## 1-3. 모델의 종류 (이 프로젝트에 나오는 것 위주)

모델은 "무엇을 입력받아 무엇을 내놓는가"로 구분하면 이해하기 쉽다.

| 종류 | 입력 → 출력 | 대표 예 | 이 프로젝트 |
|---|---|---|---|
| **언어 모델(LLM)** | 글 → 다음에 올 글 | ChatGPT, Claude, Gemma | 직접 쓰지 않음. EmbeddingGemma는 Gemma(LLM)를 바탕으로 만들었지만 글을 생성하지 않는다 |
| **임베딩 모델** | 글·사진·소리 → 숫자 목록(벡터) | EmbeddingGemma 2 | 2~8, 10단계의 주인공. 검색에 쓴다 |
| **물체 검출 모델** | 사진 → 물체 위치(박스)와 이름 | YOLO, YOLOE | 8·10단계 |
| **자세 추정 모델** | 사진 → 사람 관절 17개의 좌표 | YOLO11n-pose | 9·10단계 |
| **분류 모델** | 입력 → 정해진 이름표 중 하나 | 9-6단계 GRU (만세/손 흔들기/…) | 9-6단계에서 직접 학습 |

알아 둘 점:

- **LLM과 임베딩 모델의 차이**: LLM은 "대답을 써 준다". 임베딩 모델은 대답을 쓰지 못하고, 대신 입력의 의미를 숫자로 바꿔 "무엇과 무엇이 비슷한가"를 계산하게 해 준다. 검색에는 임베딩 모델이 맞다.
- **멀티모달**: 글·사진·소리처럼 종류가 다른 입력을 함께 다루는 모델. EmbeddingGemma 2가 멀티모달 임베딩 모델이다.
- 모델끼리 조합해 쓴다. 8단계는 "YOLO로 물체 위치를 찾고 → 그 부분을 EmbeddingGemma 2로 임베딩해 → 글로 검색"한다. 각 모델이 잘하는 일이 다르기 때문이다.

## 1-4. 학습은 실제로 무엇을 하나

시험공부에 비유하면 이해가 쉽다.

| 학습 용어 | 시험공부로 비유 | 실제 뜻 |
|---|---|---|
| 학습 데이터 | 문제집 | 입력과 정답이 짝지어진 예시들 |
| 평가 데이터 | 모의고사(문제집과 다른 문제) | 학습에 쓰지 않고 실력 확인에만 쓰는 예시 |
| loss(손실) | 채점해서 틀린 정도 | 모델의 답이 정답과 얼마나 먼지를 나타내는 숫자. 작을수록 좋다 |
| 기울기(gradient) | "이 부분을 이렇게 고치면 덜 틀린다"는 오답 노트 | 각 가중치를 어느 방향으로 바꾸면 loss가 줄어드는지 |
| 학습률(learning rate) | 오답 노트를 보고 한 번에 얼마나 크게 고칠지 | 가중치를 한 번에 바꾸는 크기 |
| batch(배치) | 한 번에 풀고 채점하는 문제 수 | 한 번에 모델에 넣는 예시 수 |
| step | 채점 후 공부 방법을 한 번 고치기 | 가중치를 한 번 수정하는 것 |
| epoch | 문제집을 처음부터 끝까지 한 바퀴 풀기 | 학습 데이터 전체를 한 번 다 보는 것 |
| 과적합 | 문제집 답만 외워서 모의고사는 못 푸는 상태 | 학습 데이터 점수만 오르고 평가 데이터 점수는 떨어짐 |

학습 한 번의 흐름은 이렇다. 이 과정을 수십~수만 번 반복한다.

```text
① 배치(예: 8문제)를 모델에 넣는다
② 모델의 답과 정답을 비교해 loss를 계산한다
③ loss를 줄이려면 각 가중치를 어느 쪽으로 바꿀지(기울기) 계산한다   ← 역전파(backpropagation)
④ 학습률만큼 가중치를 고친다                                          ← 옵티마이저(AdamW 등)
⑤ 다음 배치로 ①부터. 데이터를 다 돌면 1 epoch 끝
```

epoch를 늘리면 같은 문제집을 여러 번 푸는 것이라 점수가 오르지만, 너무 많으면 답을 외워 과적합이 된다. 그래서 epoch마다 모의고사(평가 데이터)를 봐서 점수가 떨어지기 시작하면 멈춘다.

## 1-5. 사전 학습과 미세 조정

- **사전 학습(pre-training)**: 회사가 엄청난 양의 데이터와 GPU로 모델을 처음부터 가르치는 단계. 수 주~수 개월이 걸린다. 우리가 받은 `google/embeddinggemma-2`가 사전 학습된 모델이다. 일반적인 의미 비교는 이미 잘한다.
- **미세 조정(fine-tuning)**: 사전 학습된 모델을 내 분야 데이터로 **조금 더** 가르치는 것. 가중치를 새로 만드는 게 아니라 이미 좋은 값을 살짝 고친다. 그래서 데이터가 적고(7단계 282쌍) 시간이 짧아도(4.3분) 효과가 난다.
- 비유: 사전 학습 = 대학까지 일반 교육, 미세 조정 = 입사 후 우리 회사 업무 교육.

## 1-6. 숫자와 하드웨어 기초

- **GPU**: 단순한 계산을 수천 개 동시에 하는 칩. 딥러닝은 대부분 큰 곱셈 덩어리(행렬 곱셈)라서 GPU가 CPU보다 수십 배 빠르다.
- **CUDA**: NVIDIA GPU를 프로그램에서 쓰게 해 주는 소프트웨어. 코드의 `device="cuda"`는 "GPU에서 계산하라"는 뜻이다.
- **PyTorch**: 딥러닝 계산(행렬 곱셈, 기울기 계산)을 해 주는 파이썬 라이브러리. 거의 모든 모델이 이 위에서 돈다. `import torch`.
- **숫자 형식**: 가중치 하나를 몇 바이트로 저장하느냐. 4바이트(float32)는 정밀하고, 2바이트(bfloat16)는 메모리가 절반이다. 자세한 건 2단계·7단계에서.

# 2부. 단계별 개념

## 1단계 환경 준비

**하는 일**: SSD 연결, 전원 모드·스왑 설정, Jetson용 PyTorch 설치.

**새로 나오는 개념**

- **Jetson**: NVIDIA의 작은 AI 컴퓨터. 카메라 옆에 두고 바로 AI를 돌리는 용도(**엣지 AI**)로 쓴다. 서버로 데이터를 보내지 않아도 된다.
- **통합 메모리**: 보통 PC는 CPU용 메모리와 GPU 전용 메모리가 따로 있다. Jetson은 **CPU와 GPU가 같은 8 GB를 나눠 쓴다**. 그래서 다른 학생이 모델을 올리면 내가 쓸 GPU 메모리도 줄어든다.
- **스왑**: 메모리가 모자랄 때 SSD 일부를 메모리처럼 빌려 쓰는 공간. 느리지만 프로그램이 죽는 것은 막는다.
- **JetPack / CUDA 버전**: Jetson의 운영체제 묶음. PyTorch는 이 버전에 맞는 것(cu132 휠)을 깔아야 GPU를 쓴다. 일반 PyTorch를 깔면 CPU만 쓴다.
- **venv(가상환경)**: 내 계정 전용 파이썬 패키지 공간(`~/eg2`). 다른 학생의 설치와 섞이지 않는다.

**내 결과로 보면**: L4T R39, CUDA 13.2 장비라 JetPack 7 경로로 설치했고, `check.py`로 GPU 사용 가능을 확인했다.

## 2단계 패키지·모델 설치

**하는 일**: sentence-transformers 설치, EmbeddingGemma 2 내려받기, 공통 로더 `eg2.py` 작성.

**새로 나오는 개념**

- **Hugging Face**: 모델 파일을 올리고 받는 공개 저장소(모델계의 GitHub). `"google/embeddinggemma-2"`가 그 안의 주소다.
- **transformers / sentence-transformers**: Hugging Face 모델을 읽어 쓰게 해 주는 라이브러리. sentence-transformers는 임베딩 모델 전용으로 `encode()` 한 줄이면 벡터를 준다.
- **torch 고정(`torch-pin.txt`)**: 다른 패키지를 설치할 때 pip가 Jetson용 torch를 일반 torch로 바꿔 버리지 않도록 버전을 묶어 둔다.
- **인코더**: 입력 하나를 벡터로 바꾸는 부품. EmbeddingGemma 2 안에는 텍스트·비전(사진·영상)·오디오 인코더 세 부품이 있다. `eg2.py`의 `load(vision=..., audio=...)`가 필요한 부품만 올린다. 안 쓰는 부품을 빼면 메모리를 아낀다.
- **bfloat16 / float32 / float16**: 가중치를 저장하는 숫자 형식.

| 형식 | 크기 | 표현 범위 | 정밀도 | 이 프로젝트에서 |
|---|---|---|---|---|
| float32 | 4바이트 | 매우 넓음 | 유효 숫자 약 7자리 | 7단계 학습 |
| bfloat16 | 2바이트 | float32와 같음 | 약 2~3자리 | 추론 기본값(`eg2.py`) |
| float16 | 2바이트 | 좁음(최대 65504) | 약 3자리 | **금지**. 이 모델은 중간 값이 범위를 넘어 결과가 깨진다 |

**내 결과로 보면**: 문장 하나를 넣었을 때 `(768,)`이 나왔다. "숫자 768개짜리 벡터 하나"라는 뜻이다. 270M개 × 2바이트(bfloat16) ≈ 0.54 GB인데, 6단계에서 잰 텍스트 전용 GPU 메모리가 0.52 GB로 거의 같다.

## 3단계 텍스트 테스트

**하는 일**: 문서 4개 중에서 한국어 질문에 맞는 문서를 찾는다. 이 프로젝트 검색의 기본형이다.

**새로 나오는 개념**

- **벡터와 차원**: 벡터는 숫자를 순서대로 늘어놓은 목록, 차원은 그 숫자의 개수다. `[0.12, -0.03, 0.45]`는 3차원 벡터.
- **임베딩**: 입력을 의미가 담긴 벡터로 바꾼 것. 의미가 비슷한 문장은 768차원 공간에서 가까운 곳에 놓이도록 모델이 학습돼 있다. 숫자 하나하나에 뜻이 있는 게 아니라 768개 전체의 방향이 의미를 나타낸다.
- **코사인 유사도**: 두 벡터(화살표)의 방향이 얼마나 같은지. 같으면 1, 직각이면 0, 반대면 -1.
- **정규화**: 벡터 길이를 1로 맞추는 것. 길이가 1인 벡터끼리는 곱해서 더하기(내적)만 해도 코사인 유사도가 나온다. 그래서 `normalize_embeddings=True` 후 `sim = q @ dd.T` 한 줄로 질의×문서 점수표를 만든다. `@`는 행렬 곱셈(여러 내적을 한꺼번에), `.T`는 행과 열 뒤집기.
- **검색 = 줄 세우기**: 질문 벡터와 모든 문서 벡터의 유사도를 구하고 큰 순서로 정렬한다. `row.argmax()`는 1위 위치.
- **프롬프트(SearchQuery / Document)**: 입력 앞에 붙이는 역할 안내문. 모델은 이것을 보고 "검색 질문"인지 "검색될 문서"인지 구분해 짝을 더 잘 맞춘다.
- **Matryoshka(마트료시카) 차원 줄이기**: 큰 인형 안에 작은 인형이 들어 있듯, 768개 중 **앞의** 512·256·128개만 잘라 써도 쓸 만하도록 학습된 방식. 저장 공간과 비교 계산이 줄어든다. 자른 뒤에는 길이가 1이 아니라서 다시 정규화한다(`test_text.py`의 `dd = dd / ... ** 0.5` 줄).

**내 결과로 보면**

| 차원 | "수업 중에 졸리고 머리가 맑지 않아요" → CO2 문장 | 질의 시간 |
|---|---|---|
| 768 | 0.717 (1위) | 198 ms(첫 실행 포함) |
| 256 | 0.734 (1위) | 175 ms |
| 128 | 0.785 (1위) | 174 ms |

- "졸리다"와 "CO2"는 단어가 겹치지 않는데 1위로 찾았다. 단어 일치가 아니라 **의미**로 찾는다는 증거다.
- 차원을 줄이면 점수가 오르지만 성능이 좋아진 게 아니다. 정보가 줄어 모든 문장이 서로 비슷해 보여서 다 같이 오른 것이다. 점수는 같은 차원 안에서만 비교한다.
- 시간이 같은 이유: 모델은 항상 768개를 다 계산한 뒤 자른다. 이득은 계산 시간이 아니라 저장 공간이다(문서 100만 개 기준 약 3 GB → 0.5 GB).

## 4단계 영상 테스트

**하는 일**: 글로 쓴 질문으로 사진·동영상을 찾는다.

**새로 나오는 개념**

- **같은 벡터 공간**: 텍스트 인코더와 비전 인코더가 같은 768차원 공간에 벡터를 놓도록 함께 학습됐다. 그래서 글 벡터와 사진 벡터를 3단계와 똑같은 유사도 계산으로 비교할 수 있다. 이것이 멀티모달 검색의 핵심이다.
- **동영상 = 사진 여러 장**: 동영상은 1초에 1장씩 뽑은 프레임들을 모델에 넣는다(README "비디오 기본 1 fps").
- **디코더**: 압축된 영상 파일(mp4)을 사진으로 풀어 주는 프로그램(FFmpeg, PyAV). 모델과는 별개의 준비 단계다.

**내 결과로 보면**: "사람이 아무도 없는 빈 공간"은 사람 없는 사진 3장을 1~3위로 정확히 골랐다. "두 사람이 함께 있는 장면"은 1위는 맞았지만 다른 두 사람 사진(04)은 사람 없는 사진과 점수 차가 0.01 안쪽이었다. 임베딩 검색은 "있다/없다"는 잘하고 "몇 명"은 약하다. 점수도 0.58~0.67에 몰렸다.

## 5단계 음성 테스트

**하는 일**: 글로 쓴 질문으로 소리 파일을 찾는다.

**새로 나오는 개념**

- **샘플레이트 16 kHz**: 소리를 1초에 16,000번 재서 숫자로 저장했다는 뜻. **모노**는 채널 1개. 모델이 이 형식으로 학습돼서 다른 형식이면 결과가 엉망이 된다.
- **파형**: 소리를 시간에 따른 숫자 목록으로 본 것. `make_sounds.py`는 사인파(삐 소리)와 잡음을 숫자로 직접 계산해 만들었다.

**내 결과로 보면**: 경보음·소음은 맞혔고, "에어컨을 켜 달라는 말"처럼 녹음 속 단어가 든 질문은 확실히 맞혔다. "사람이 말하는 목소리"처럼 소리 종류를 묻는 질문은 틀렸다. 파일이 3개뿐이라 잠정 결론이다.

## 6단계 성능 측정

**하는 일**: 부품 구성별로 메모리·속도·GPU 사용률을 같은 방법으로 잰다.

**새로 나오는 개념**

- **지연(latency)**: 입력을 넣고 결과가 나올 때까지의 시간.
- **첫 호출이 느린 이유(워밍업)**: 첫 실행 때 GPU 준비 작업이 섞인다. 그래서 측정은 2회차 값을 쓰고, 서비스는 시작할 때 한 번 미리 돌려 둔다.
- **GPU 사용률**: GPU가 바쁜 시간의 비율. 낮으면 GPU가 아니라 다른 곳(준비, 파이썬)이 느린 것이다.
- **고정 비용**: 모델 크기와 무관하게 CUDA·PyTorch를 올리는 것만으로 드는 메모리.
- **OOM(Out Of Memory)**: 메모리 부족으로 프로그램이 죽는 것.

**내 결과로 보면**

| 구성 | 장비 RAM 증가 | GPU 메모리 최대 | 지연(2회차) | GPU 사용률 평균 |
|---|---|---|---|---|
| 텍스트 전용 | +1676 MB | 0.52 GB | 질의 2개 172 ms | 16% |
| +비전 | +1646 MB | 1.2 GB | 사진 5장 3179 ms | 96% |
| +오디오 | +1701 MB | 1.13 GB | WAV 3개 395 ms | 66% |
| 전체 | +1935 MB | 1.77 GB | 혼합 6621 ms | 91% |

- 텍스트 전용도 RAM이 1.7 GB 늘었는데 가중치는 0.52 GB뿐이다. 나머지는 고정 비용이다. 학생 한 명이 모델을 올릴 때마다 약 1.7 GB가 든다는 뜻이라, 2~3명이 동시에 돌리면 8 GB가 빠듯해진다.
- 텍스트는 GPU가 16%만 일했다. 계산량이 작아 GPU가 놀고 있다. 사진은 96%로 GPU 계산 자체가 병목이다.
- 오디오 1회차 3016 ms → 2회차 395 ms. 워밍업 효과다.

## 7단계 도메인 미세 조정

**하는 일**: 강의실 질문-문서 쌍으로 텍스트 모델을 추가 학습하고, 학습 전후 검색 점수를 비교한다. 이 프로젝트에서 처음으로 **학습**을 한다. 1부 1-4·1-5를 먼저 읽고 오면 좋다.

**새로 나오는 개념**

- **도메인**: 특정 분야. 여기서는 강의실 환경(CO2, 냉난방, 센서, 경보 등).
- **학습/평가 데이터 분리**: `train.jsonl` 282쌍(문서 94개)으로 배우고, `eval.jsonl` 60쌍(문서 20개)으로 시험 본다. 두 파일은 하나도 겹치지 않는다. 한 줄은 `{"anchor": 질문, "positive": 정답 문서}`.
- **이 학습의 loss (MultipleNegativesRankingLoss)**: 배치에 쌍 8개를 넣으면, 질문 1번의 정답은 문서 1번이고 나머지 문서 7개는 자동으로 오답이 된다. "질문-정답은 가깝게, 질문-오답은 멀게" 만드는 방향으로 가중치를 고친다. 오답을 따로 만들 필요 없이 질문-정답 쌍만 있으면 된다. 같은 배치에 같은 문서가 두 번 들어가면 정답이 오답 취급되므로 `NO_DUPLICATES`로 막는다.
- **MatryoshkaLoss**: 위 loss를 768/512/256/128차원에서 모두 계산해 더한다. 학습 후에도 잘라 쓰는 성질이 유지된다.
- **설정값(하이퍼파라미터)**: 사람이 학습 전에 정하는 값. `train_ft.py` 위쪽에 모아 뒀다.

| 설정 | 값 | 뜻 |
|---|---|---|
| `EPOCHS` | 3 | 문제집 3바퀴 |
| `BATCH` | 8 | 한 번에 8쌍. 클수록 오답이 많아 효과가 크지만 메모리를 더 씀 |
| `ACCUM` | 2 | 배치 2개의 기울기를 모아 한 번 고침(기울기 누적) → 실제로는 16쌍마다 1번 수정 |
| `LR` | 2e-5 (0.00002) | 학습률. 미세 조정은 원래 능력을 지키려고 작게 잡는다 |
| `warmup_steps` | 0.1 | 처음 10% 동안 학습률을 0에서 천천히 올려 초반에 크게 흔들리지 않게 |

  step 수 계산: 282쌍 ÷ 16 ≈ 18번/epoch × 3 epoch = **54 step**. 실제 로그도 54 step이었다.

- **학습 때 메모리를 더 쓰는 이유**: 가중치 외에 기울기, 옵티마이저 기억값(AdamW는 가중치마다 숫자 2개), 역전파용 중간 계산값을 들고 있어야 한다. 줄이는 방법 두 가지를 썼다.
  - **gradient checkpointing**: 중간 계산값을 버렸다가 필요할 때 다시 계산한다. 메모리 대신 시간을 쓴다.
  - **입력 임베딩 고정**: 단어 → 벡터 변환 표는 모델에서 큰 부분인데, 이것을 학습하지 않으면 그만큼 기울기·옵티마이저 기억값이 필요 없다.
- **학습은 float32로**: bfloat16은 유효 숫자가 2~3자리라 0.1234 같은 가중치에 0.00002만큼 더해도 반올림돼 사라진다. 그래서 가중치 보관은 float32, 계산은 `bf16=True`로 빠르게 했다. 저장된 모델이 약 1.1 GB(270M × 4바이트)인 이유다.
- **평가 지표**
  - **accuracy@k**: 정답이 상위 k개 안에 든 질문의 비율. @1은 1위 적중률.
  - **nDCG@10**: 정답이 **몇 위**인지까지 반영한 점수. 1위면 1.0, 2위면 0.63, 3위면 0.5처럼 내려가고 10위 밖이면 0. accuracy@1은 2위와 10위를 똑같이 "틀림"으로 보지만 nDCG는 2위에 부분 점수를 준다.
- **일반 성능 확인**: 미세 조정 후 강의실 밖 일반 문장 검색이 망가지지 않았는지도 본다(`eval_ir.py`의 일반 문장 8쌍).

**내 결과로 보면**

- 학습: 4.3분, GPU 메모리 최대 3.45 GB(추론 0.52~0.66 GB의 약 5~6배). loss 2.84 → 약 0.05~0.08로 줄었다(4개 차원 loss를 더한 값이라 절대값보다 줄어드는 추세를 본다).
- epoch별 accuracy@1: 0.917 → 0.933 → 0.933. 떨어지지 않았으니 과적합 없음.

| 차원 | accuracy@1 학습 전 → 후 | 60문제 중 | accuracy@3 | nDCG@10 |
|---|---|---|---|---|
| 768 | 0.850 → 0.933 | 51 → 56개 | 0.967 → 1.000 | 0.937 → 0.973 |
| 256 | 0.767 → 0.917 | 46 → 55개 | 0.967 → 1.000 | 0.903 → 0.967 |
| 128 | 0.767 → 0.850 | 46 → 51개 | 0.917 → 1.000 | 0.890 → 0.940 |

- 학습 전에도 정답은 대부분 3위 안에 있었고, 학습이 그것을 1위로 끌어올렸다.
- 학습 후 128차원(0.850)이 학습 전 768차원(0.850)과 같아졌다. 벡터를 1/6로 줄여도 원래 성능이 나온다.
- 일반 문장은 학습 전후 모두 1.000. 원래 능력을 잃지 않았다.
- 텍스트 인코더만 학습했기 때문에 이 모델로는 사진을 검색할 수 없다. 그래서 8단계부터는 원본 모델을 쓴다.

## 8단계 웹캠 물체 추출과 웹 검색 (진행 중)

**하는 일**: 웹캠에서 물체를 찾아 잘라 저장하고, 브라우저에서 "빨간 텀블러" 같은 글로 검색한다. YOLO만 쓴 결과의 문제를 확인한 뒤 두 가지로 개선한다.

**새로 나오는 개념**

- **물체 검출**: 사진에서 물체가 **어디**(박스) 있고 **무엇**(클래스)인지 찾는 일. YOLO가 한다. 임베딩 모델은 "무엇과 비슷한가"만 답하고 위치는 모른다. 그래서 두 모델을 이어 쓴다.

  ```text
  웹캠 프레임 ─▶ YOLO(박스 찾기) ─▶ 박스 부분 자르기(크롭) ─▶ EmbeddingGemma 2(512차원 벡터) ─▶ 저장
  브라우저 검색어 ───────────────────────────────▶ EmbeddingGemma 2 ─▶ 저장된 벡터와 비교 ─▶ 결과
  ```

- **클래스와 COCO 80종**: 기본 YOLO는 COCO라는 데이터셋의 80가지 이름만 배웠다. 그 밖의 물체(세탁기 등)는 아는 이름 중 비슷한 것(oven)으로 잘못 붙인다. 모델은 배운 것만 안다는 한계를 직접 확인하는 단계다.
- **개선 1, 재라벨(relabel)**: YOLO가 붙인 이름 대신, 크롭 임베딩과 라벨 문구들의 유사도로 이름을 다시 붙인다. 3단계 검색을 이름 붙이기에 쓴 것이다.
- **개선 2, YOLOE(오픈 어휘 검출)**: 찾을 물체 이름을 글로 지정할 수 있는 검출기. 80종 제한이 없다.
- **신뢰도(conf)**: 검출기가 "이 박스가 맞다"고 확신하는 정도(0~1). `--conf 0.5`면 그보다 낮은 박스는 버린다. 낮추면 더 많이 찾지만 오검출도 늘어난다.
- **추적(track)**: 프레임이 바뀌어도 같은 물체에 같은 ID를 붙인다. 같은 물체를 매 프레임 다시 저장하지 않으려고 쓴다.
- **스레드**: 한 프로그램 안에서 일을 동시에 나눠 하는 작업 줄. 카메라 읽기·검출 / 임베딩 / 웹 서버가 서로 기다리지 않게 나눴다.
- **웹 서버(FastAPI)**: 브라우저 요청에 답하는 프로그램. `/stream`은 실시간 영상, `/search?q=`는 검색.
- **fps**: 1초에 처리하는 프레임 수. 실시간 처리의 속도 지표다.

## 9단계 사람 동작·행동 인식

**하는 일**: 사람의 관절 좌표로 만세·손 흔들기·악수를 판정한다. 처음에는 규칙으로, 마지막에는 학습한 모델로.

**새로 나오는 개념**

- **자세 추정(pose estimation)**: 사진에서 사람의 관절 17개(코, 눈, 어깨, 팔꿈치, 손목, 엉덩이 등) 좌표를 찾는 일. YOLO11n-pose가 한다. 사람 사진 대신 관절 좌표만 다루므로 개인정보 부담도 적다.
- **규칙 기반 vs 학습 기반**: 9-1·9-2는 사람이 기준을 정한다("손목이 어깨보다 위"). 9-6은 예시 데이터로 기준을 학습한다(1-1 참고). 규칙으로 쓰기 어려운 동작(박수, 팔짱)도 녹화만 하면 추가할 수 있다.
- **정규화(거리 기준 맞추기)**: 카메라에서 멀면 사람이 작게 보인다. 모든 거리를 어깨 너비로 나눠 가까이 있든 멀리 있든 같은 기준을 쓴다. 3단계의 벡터 정규화(길이를 1로)와 대상은 다르지만 "크기 기준을 맞춘다"는 생각은 같다.
- **시간 정보**: 손 흔들기는 한 장의 사진으로는 알 수 없고 여러 프레임에 걸친 움직임으로만 알 수 있다. 9-2는 0.6초 다수결로 판정이 깜빡이는 것을 막는다.
- **특징(feature)**: 모델에 넣기 좋게 원래 데이터에서 뽑은 숫자. 9-3은 프레임마다 관절 관련 숫자 53개를 CSV로 기록한다.
- **라벨**: 학습 데이터의 정답 이름표. 파일 이름(wave.csv → "wave")이 라벨이다.
- **윈도**: 연속된 프레임 몇 개를 한 덩어리로 자른 것(동작 30프레임. README는 약 1.5초라 했지만 내 환경 약 12 fps에서는 약 2.5초).
- **GRU**: 순서가 있는 데이터(시간에 따른 프레임들)를 차례로 읽으며 앞 내용을 기억하는 작은 신경망. 윈도 전체를 보고 라벨 하나를 고른다(분류 모델). 7단계는 이미 있는 큰 모델을 미세 조정했다면, 9-6은 **작은 모델을 처음부터 학습**한다. epoch·batch·loss·평가 데이터 분리는 7단계와 똑같이 적용된다.
- **닫힌 라벨 집합**: 분류 모델은 배운 라벨 중에서만 고른다. "모르겠다"는 답이 없어서, 배우지 않은 동작에도 가장 비슷한 라벨을 높은 확률로 고른다. 8단계 YOLO가 세탁기를 oven이라 부른 것과 같은 한계다.
- **혼동 행렬**: 행은 정답, 열은 모델의 예측인 표. 대각선이 맞힌 개수이고, 나머지 칸은 "무엇을 무엇으로 헷갈렸는지"를 보여 준다. 어떤 데이터를 더 녹화할지 정하는 근거가 된다.

**내 결과로 보면** (자세한 표는 report/results_step9.md)

- 9-1 raw(약 12 fps): 판정이 깜빡여 악수 1번이 11번, 만세 시도 한 번이 만세↔한팔들기 6번으로 기록됐다. 손 흔들기는 한팔들기로만 나왔다.
- 9-2 smooth: 0.6초 다수결로 만세·한팔들기·악수가 정확히 1번씩 잡혔다. 손 흔들기는 손목이 "어깨보다 0.3 어깨너비 위"일 때만 인식됐다. 규칙은 정한 기준대로만 동작한다.
- 9-6 1차(4라벨: idle, wave, clap, arms_crossed): 검증 정확도 0.932였지만 실시간에서는 동작 5번에 20건이 기록되고 만세·한팔들기가 사라졌다. 배우지 않은 만세를 wave 등으로 확신하며 답했고(닫힌 라벨 집합), 모델 판정도 깜빡였다.
- 9-6 2차(6라벨: 만세·한팔들기와 손이 몸 앞에 있는 idle 추가, 앱 v3에 모델 판정 다수결): 검증 0.861로 숫자는 내려갔지만 실시간 기록이 12건으로 줄고 6가지 동작을 모두 인식했다. 규칙이 없는 박수·팔짱도 녹화만으로 배웠다.
- 검증 점수가 높아도 실시간 성능은 다를 수 있다. 검증이 같은 사람·같은 녹화의 뒷부분이기 때문이다(7단계에서 학습·평가 데이터를 겹치지 않게 나눈 이유와 같다).
- 9-5 행동 패턴: 지나감·힐끗 봄·관심 있음은 맞았다. 옆을 보며 서 있기는 체류 9초로 머무름 기준(10초)에 1초 모자라 지나감이 됐다. 녹화 숫자로 확인하니 서 있는 동안 속도는 0.13~0.21로 기준(0.5)보다 낮아, 규칙 자체는 맞게 동작했다.
- 9-6 행동 모델(passing·glance·interested 각 10번 녹화): 검증 0.967이었지만 실시간은 4개 중 2개로 규칙(3개)보다 나빴다. 옆을 보며 서 있었는데 "관심 있음"이라 했다. 배운 데이터에서 멈춰 있던 것이 interested뿐이라 "멈춤 = 관심"이라는 **지름길**을 배운 것이다. 데이터가 적으면 모델은 우리가 의도한 이유(정면을 봄)가 아니라 가장 쉬운 차이(멈춤)로 구분한다. 기준이 분명한 문제는 규칙이, 규칙으로 적기 어려운 문제(박수·팔짱)는 학습이 낫다.

## 10단계 카메라 2대 접근 감지

**하는 일**: 카메라 2대로 사람과 타겟 물체의 실제 위치(미터)를 구하고, 가까워지면 알람을 울린다. 예: 소화기 1m 안으로 사람이 들어오면 "근접", 3m 밖으로 나가면 "이탈".

**왜 카메라가 2대인가**: 사진은 평면이라 카메라 1대는 사람이 '어느 방향'에 있는지만 알고 '몇 m'인지는 모른다. 발이 바닥(높이 0)에 닿아 있다고 가정하면 발목으로 거리를 짐작할 수 있지만, 교실에서는 책상에 발이 가려져 실패한다(10-3에서 직접 확인). 그래서 책상 위로 보이는 어깨를 두 카메라가 다른 방향에서 보고, 두 시선이 만나는 점을 계산한다.

**진행 순서**

| 단계 | 하는 일 | 한 줄 이유 |
| --- | --- | --- |
| 10-1 렌즈 보정 | 체커보드를 비춰 렌즈 휘어짐·초점 거리 측정 | 휜 화면 그대로 계산하면 위치가 틀어진다 |
| 10-2 위치 보정 | 테이프 기준점을 줄자로 재고 화면에서 클릭 | 카메라가 교실 어디서 어느 방향을 보는지 알아야 시선을 그릴 수 있다 |
| 10-3 문제 확인 | 카메라 1대 + 발목 | 앉거나 책상 뒤면 틀린다는 것을 확인 |
| 10-4 개선 | 카메라 2대 + 어깨 삼각측량 | 앉아도 위치가 맞고, 높이로 앉음/섬 구분 |
| 10-5 보완 | 한 카메라에만 보이면 어깨 높이 1.2m 가정 | 추적이 끊기지 않게 (대신 오차 큼) |
| 10-6 접근 알람 | 타겟을 글로 찾고 걷기·지나가기·앉기 시나리오 시험 | 실제 쓰임새 확인 |
| 10-7 비교 / 10-8 이동 타겟 | 방식별 표 정리 / 움직이는 카트와 충돌 예상 시간 | 정리와 확장 |

**이 단계에는 학습이 없다**: 7·9단계처럼 모델을 새로 학습하지 않는다. 이미 학습된 모델(관절 추정, YOLOE, EmbeddingGemma)이 내놓은 화면 좌표에 기하 계산(보정, 삼각측량)을 더해 실제 거리로 바꾸는 단계다.

**좌표계**: 강의실 바닥 기준. 원점 = 바닥의 한 점(벽 모서리 추천), x = 한 벽을 따라가는 방향, y = 원점에서 x를 바라볼 때 왼쪽, z = 위, 단위 m. README(x = 칠판 따라 오른쪽, y = 교실 뒤쪽)는 y가 오른쪽이 되는 경우라 그러면 왼손 좌표계(거울상)라 solvePnP가 "뒤를 보는 카메라"를 답으로 내서 바꿨다. 좌표계는 x→y→z 순서로 오른손 법칙(엄지 x, 검지 y, 중지 z)을 따라야 한다.

**지원 님 장비**: USB 웹캠 1대 + IP 카메라 1대. 삼각측량은 두 카메라 종류가 달라도 된다(각자 10-1로 렌즈를 재기 때문). 다만 IP 카메라 영상은 압축·네트워크 때문에 수백 ms 늦게 도착하므로, 두 카메라가 '같은 순간'을 보도록 `--lag`로 지연을 빼 준다. 걷는 사람(약 1 m/s)은 0.3초 어긋나면 위치가 약 30cm 틀어진다.

**새로 나오는 개념**

- **렌즈 보정(intrinsics)**: 웹캠 렌즈는 화면 가장자리를 휘게 찍는다. 체커보드를 여러 각도로 찍어 휘어짐과 초점 거리를 계산해 둔다. 카메라마다 1회.
- **위치 보정(extrinsics)**: 카메라가 교실의 어디에서 어느 방향을 보는지 계산한다. 줄자로 잰 바닥 기준점을 화면에서 클릭해 구한다. 보정 후 카메라를 움직이면 다시 해야 한다.
- **삼각측량**: 두 눈으로 거리를 느끼는 원리. 두 카메라에서 같은 점(어깨 중심)을 보면 두 시선이 만나는 곳이 실제 3D 위치다. 카메라 1대로는 방향만 알고 거리를 모른다.
- **재투영 오차**: 계산한 3D 위치를 다시 각 카메라 화면에 그려 봤을 때 실제 점과 몇 픽셀 차이 나는지. 작을수록 정확하고, 두 카메라의 같은 사람을 짝지을 때도 쓴다.
- **히스테리시스**: 경계에서 알람이 켜졌다 꺼졌다 깜빡이지 않도록, 켜는 기준과 끄는 기준을 조금(0.2 m) 다르게 두는 것.
- **칼만 필터**: 흔들리는 측정값과 "이전 위치·속도로 예측한 값"을 섞어 위치와 속도를 부드럽게 추정하는 방법. 한두 프레임을 놓쳐도 예측으로 이어 간다.
- **TTC(충돌 예상 시간)**: 지금 거리 ÷ 다가오는 속도. "이대로면 몇 초 뒤 닿는가".
- **모델 조합의 완성**: 타겟은 YOLOE가 후보를 찾고 EmbeddingGemma 2가 글 설명과 가장 닮은 후보를 고른다(8단계). 사람 위치는 자세 추정의 어깨 중심을 쓴다(9단계). 앞 단계들이 모두 모인다.

**내 결과로 보면** (자세한 표는 report/results_step10.md)

- 10-1 렌즈 보정: USB 0.215 px, IP 0.291 px. 처음 IP는 3.6 px였는데, 모서리를 다듬는 창(11 px)이 체커보드 칸보다 커서였다. 창을 칸 크기에 맞추자 해결됐다.
- 10-2 위치 보정: 첫 장소는 기준점이 40x50 cm 안에 몰려 카메라 위치가 50~60 cm 틀렸다. 새 장소는 14개를 넓게 붙였지만 재투영 5.6~6.6 px, 카메라 위치 42~131 cm 차이로 여전히 기준 미달이었다. 그래도 기준점 대부분의 삼각측량 오차는 10 cm 이하라 그대로 진행했다.
- 10-3 발목(카메라 1대): 근접 알람은 됐지만, 2 m 밖으로 가기 전에 발목을 놓쳐 이탈 알람이 한 번도 안 떴다.
- 10-4 어깨 삼각측량(카메라 2대): 의자 옆 0.54 m, '섬'으로 맞게 나왔다. 카메라 가까이 가면 한쪽 화면에서 몸이 잘려 위치가 사라졌다.
- 10-5 한 카메라 추정: 거의 동작하지 않았다. 보정에서 카메라 높이가 1.0~1.2 m로 계산돼, '어깨 높이 1.2 m' 평면에 내려다보는 시선이 닿지 않았기 때문이다. 계산 방식에는 전제(카메라가 어깨보다 높다)가 있고, 보정이 틀리면 그 전제가 깨진다.
- 10-6 글로 타겟 찾기: "chair"로 두 카메라 모두에서 의자를 찾았고, 줄자 위치와 3 cm 차이였다. 물체는 사람보다 삼각측량이 잘 맞았다.
- 속도: 카메라 1대 24.7 fps, 2대 약 19.5 fps. 글 타겟 모델까지 올리면 RAM 1.8 GB → 3.7 GB.
